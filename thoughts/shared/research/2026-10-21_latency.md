# Latency

Pipeline: stk1160 (vb2 queue, 8 buffers min) -> `v4l2-ctl --stream-mmap` -> pipe ->
camserver.py `pump()` -> ffmpeg (separatefields, mjpeg, mpjpeg) -> camserver `read_stream()`
(field hold) -> HTTP `/stream.mjpg` -> SSH tunnel -> Amiga-View `StreamClient` -> `VideoView`
layer.

## Method

- Driver queue: `strace -ttt -T -v -e ioctl` on the running v4l2-ctl. Each `VIDIOC_DQBUF`
  return time (entry + duration, realtime) against the buffer's own timestamp
  (`TIMESTAMP_MONOTONIC | TSTAMP_SRC_EOF`, converted with `time.time() - time.monotonic()` read
  on the Pi at the same moment). This is "end of frame (end of its second field) to v4l2-ctl
  has it".
- HTTP out: a timestamped client on the Pi (`/tmp/lat/client.py`, one extra client) against the
  same DQBUF trace: for each part, its arrival minus the EOF timestamp of the newest frame
  dequeued before it. This is a lower bound (a part from an older frame would read low), so it is
  only valid once the pattern is known: after the fix the two fields of every frame land at
  ~10 ms and ~29 ms, period 20 ms, which rules out an older frame.
- ffmpeg delay: the stream encoder command fed 4 frames 300 ms apart offline
  (`/tmp/lat/enc.py` on the Pi), part times printed.
- Mac: the same lower-bound client through the app's SSH tunnel (127.0.0.1:8090), Pi clock
  offset from the minimum-RTT sample of 30 round trips over one ssh session (error +-7 ms).
- Shell commands and scripts: scratchpad `maclat.py`; Pi `/tmp/lat/{client,ana,ana2,enc}.py`.

## Before (measured)

| Stage | ms | Evidence |
|---|---|---|
| Driver done queue (EOF -> DQBUF) | 174 / 188 / 228 (min/med/max) | 100 frames; DQBUF gap 40.0 ms where the stk1160 delivers every 39.7 ms |
| v4l2-ctl write of each frame | blocked ~39 ms each | the consumer, not the source, paced the loop |
| ffmpeg stream encoder | 3 fields held, ~60 ms | frames 0-3 gave 1, 1, 2, 2 parts; the rest only at EOF |
| camserver field hold | 20 ms on EVERY field once backed up | client gaps median 20.0 ms exactly |
| Pi total, frame end -> HTTP out | ~250-270 | sum of the above |

Root cause 1 (the big one): `read_stream()` held any part arriving under half a period after
the previous one. Once anything was behind, the next frame's first field also arrived straight
after the held second field, so every field waited 20 ms: output paced at exactly
2 x `--fps 25` = 50.0 fields/s against the grabber's 50.38. The 0.38 fields/s surplus filled
the driver's vb2 queue (~4.7 frames) and it never drained; the driver then dropped frames at the
tail. Root cause 2: the mjpeg encoder's default frame threading keeps 3 fields in flight.

## Fix (Pi, ~/amiga/camserver.py; backup camserver.py.bak-2026-10-21-latency)

- Hold only the second of a back-to-back pair: a part that follows a held part goes out at
  once. (A first version counted parts even/odd; ffmpeg's first part put that off by one and
  nothing was held: gaps 38/2 ms. The self-synchronising rule fixed it.)
- `-thread_type slice` on the stream encoder: both fields out within ~10 ms of their frame,
  still 217 fields/s of capacity on the Pi 4 (benchmark; 50.4 needed).

## After (measured)

| Stage | ms |
|---|---|
| Driver done queue (EOF -> DQBUF) | -1 / 0.1 / 0.3 (no backlog; DQBUF now waits for the frame) |
| First field EOF -> HTTP out on the Pi | median 9.7 (first field itself ended ~20 ms before EOF: ~30 ms from its capture) |
| Second field EOF -> HTTP out | median 28.5 (20 ms of it the deliberate hold that spaces the pair) |
| Tunnel to the Mac | within the +-7 ms clock error: first 5.9, second 27.0 median |
| Rate | 251-252 parts / 5 s, short_frames delta 0, restarts 0 |

Each field now leaves the Pi ~30 ms after its capture ended (was ~250+).

## Mac app (code read; not instrumented)

- `URLSession` delegate on a serial `OperationQueue`; `MultipartParser.feedNewest` keeps the
  newest part of each chunk; no frame pacing timer, no AVPlayer.
- Before: every decoded frame was a separate `DispatchQueue.main.async`, so a busy main thread
  would queue old frames and show them late one by one; and the `CGImage` was lazy, so the JPEG
  was decoded on the main thread at Core Animation's first draw.
- Changed: `LatestSlot` (one-item mailbox, the newest frame replaces a waiting one, one main hop
  at a time) and `kCGImageSourceShouldCacheImmediately` (decode on the network queue).
  Not measured whether the main thread ever backed up; this removes the possibility.
- Left: `layer.contents` shows at the next display refresh plus the compositor, ~1-2 refreshes
  (8-33 ms at 60 Hz), inherent.

## Not measured

Glass-to-glass (Amiga output -> composite -> Mac screen) needs a camera or a light sensor on
both screens; not possible without the owner. Estimate: ~30 ms Pi + ~5 ms tunnel + ~8-33 ms
display = ~45-70 ms after field capture, against ~290-320 ms before.

## Notes

- The driver keeps 8 buffers (STK1160_MIN_VIDEO_BUFFERS); empty queued buffers cost no latency.
  They only cost latency when the consumer is slower than the source, which the hold made true.
  Left unchanged.
- camserver.py is not in this repo; the repo copies live in
  ~/Code/UpRough/Up_Rough_Demo_System/tools/amiga_cam/camserver.py and its forks (not updated).

## Iteration 2 (2026-10-21): fields delivered as they complete

### Change
- Driver `pi/stk1160/` (commit a5f8790): `V4L2_FIELD_ALTERNATE` support. In alternate mode every
  field marker (0xc0 / 0x80) completes the previous field's buffer, `vb.field` is TOP/BOTTOM, lines
  are contiguous, height is the field height. Default stays INTERLACED. The isoc packet layout
  (`stk1160_isoc_layout`) is unchanged. `fieldfix_test.c` covers both modes.
- camserver `pi/camserver.py` (commit 33343e0): `--fields alternate|interlaced` (default alternate).
  Alternate mode reads 50 field buffers/s, drops `separatefields` and the 20 ms hold of the second
  field. `setup_device` always passes an explicit `field=`.

### Measured (Pi, strace DQBUF + HTTP client timestamps)
| | first field | second field |
|---|---|---|
| before: field end to HTTP part out | ~30 ms (9.8 ms after frame EOF, field ended ~20 ms earlier) | 28.4 ms |
| after | 6.4 ms median (min 5.9, max 13.5) | 6.4 ms |

DQBUF lag median 0.1 ms; 50.3 buffers/s; parts5s 252; lost delta 0; short_frames 0; restarts 0.
Picture check: alternate and interlaced gave identical statistics (720x288, mean 169.5, vertical
difference 15.3, top 16 rows 167.6, bottom 16 rows 166.3), so no shift or garbage.
The remaining 6.4 ms is the pipe plus ffmpeg MJPEG encode.

### Gotcha: the driver keeps the last format
After an alternate run, a camserver that does not pass `field=` gets alternate buffers in an
interlaced pipeline (half-black fields). The repo camserver always sets `field=`. Older copies
(UpRough) need `field=interlaced` in their `v4l2-ctl --set-fmt-video`, or a module reload.

### Rollback
`--fields interlaced` on the camserver command line, or restore
`~/amiga/camserver.py.bak-2026-10-21-iter2` and `~/stk1160-build/stk1160.ko.dbba939`.

### Network: SSH tunnel jitter (not fixed)
Inter-part gaps over 400 parts (ideal 20 ms):
- direct TCP (NODELAY relay on the Pi): p50 19.6, p99 31-34, max 41 ms.
- app tunnel (`ssh -N -L`): p99 42-64, max 50-112 ms, 10-31 gaps over 40 ms.
- `ssh -N` versus `ssh -N -o IPQoS=lowdelay`, two runs each: p99 49.0/37.8 versus 41.1/50.3,
  over-40 ms gaps 7/3 versus 5/13. No consistent gain, so Tunnel.swift is unchanged.
The Mac is on WiFi (ping RTT min 5.8, avg 9.3, max 22.7 ms); most bunching likely comes from WiFi.
Ethernet on the Mac, or a direct (non-SSH) LAN connection, are the candidates. Neither is measured.

### Mac presentation (reasoning, not measured)
VideoView sets `layer.contents` in an explicit CATransaction; WindowServer composites at vsync.
CAMetalLayer with `displaySyncEnabled = false` matters only direct-to-display. A possible gain is a
120 Hz request on the ProMotion display (NSView display link `preferredFrameRateRange`), which
halves the worst-case wait for the next refresh from 16.7 to 8.3 ms. Not tried.
